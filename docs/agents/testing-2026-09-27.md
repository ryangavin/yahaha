# Testing: how the suite is organised today, and a targeted set of changes

Companion to `review-2026-09-27.md` (Round 2, D7) and `review-handoff-2026-09-27.md` (Track T). Measured on `develop` at `a394688` plus the CI workflow on `build/linux-ci`.

## 1. Where the suite stands

| Fact | Number |
|---|---|
| `#[test]` functions | 1,100 |
| Tests that pass with zero assertions when `corpus/` or `soundfonts/` is missing (script over every test body, heuristic) | about 426 (39%) |
| Sites that print "corpus missing; skipping" or "no corpus" and return | 107 |
| Tests marked `#[ignore]` | 8 |
| Fixture functions that build a corpus engine or session | 52 (24 with the same eight-line body) |
| Test `Sink` implementations | 18, in six shapes |
| Copies of the `EngineLoop` stepping loop | 10 |
| Counting-allocator harness files (`tests/*_no_alloc.rs`) | 9, five byte-identical |
| Committed fixtures | `docs/fixtures/{library,state}.json`, `tests/golden/*.digest` (six corpus styles, hashes only), `tests/oracle/scores.txt` |
| Synthetic generators already in the tree | `multipad::synthetic::demo_bank()`, `patches::sf2::tiny_sound_font()` |
| Style or SoundFont files in git | none (`corpus/` and `soundfonts/` are git-ignored; the styles are Yamaha's) |

What this means in practice:

- **CI is green on both runners while about 40% of the suite is vacuous.** Neither the Linux nor the macOS job has a corpus, so every corpus test returns early. `AGENTS.md` says so in one sentence; nothing in the output does. A regression in chord following, section timing or the mixer cannot fail CI today.
- **The Linux port is done right at the platform edge** (`midi/null.rs`, the `rt`/`perf` shims, plugins behind `cfg(target_os = "macos")`), so almost every test that does not touch AU plugins or CoreMIDI can run on Linux. The thing keeping them from being meaningful there is fixtures, not the platform.
- **The strongest tests in the repo are the ones with no file dependency**: the recognizer golden table, the CASM/NTT rules, the `Takeover` and `swung_tick` state machines, the counting-allocator tests, the byte-flip fuzz of the SFF parser. The pattern to extend is theirs.
- **Golden snapshots are digest-only** because the listings would transcribe Yamaha patterns. That is correct for the corpus, and it is also why a golden diff is unreadable in a PR: a reviewer sees a changed hash, never a changed note.

## 2. Idiomatic Rust test organisation, and where the repo departs from it

Conventions the Rust ecosystem settled on:

1. **Unit tests live next to the code they test** (`#[cfg(test)] mod tests` in the same file) *when they need private items*, and they stay small. A test module that outgrows the code it sits under moves to `mod tests;` in `<module>/tests.rs`, still inside the crate and still able to see `pub(crate)` items.
2. **Integration tests in `tests/`** exercise the public API only, one file per concern, with shared helpers in `tests/common/mod.rs` (a module, not a test target).
3. **Fixtures are committed and small**, under `tests/fixtures/` (or `testdata/`), read with `env!("CARGO_MANIFEST_DIR")`. Anything that cannot be committed is a separate tier, marked `#[ignore = "why"]` so the default run reports it as ignored rather than passed.
4. **Skipping is explicit.** Rust has no runtime skip, so the idiom is `#[ignore = "reason"]` plus `--include-ignored` (or `--ignored`) for the environment that has the dependency. A test that decides at runtime it cannot run either panics with a clear message or is not in the default set.
5. **Hardware and network tests are opt-in** by ignore attribute or by a cargo feature, never by a silent early return.
6. **Snapshot tests** commit the expected output and show a diff on change (`insta`, or a hand-rolled golden as here), which only works when the expected output may be committed.
7. **Property tests** (`proptest`) for parsers and pure transforms: round-trips, idempotence, "never panics on arbitrary bytes".
8. **One test runner behaviour to rely on**: `cargo test` runs tests in one process per test binary, in parallel threads. `cargo-nextest` runs each test in its own process, reports skipped and flaky tests distinctly, and supports filtersets (`-E 'test(corpus)'`), which is the practical way to run a tier by name.

Where yahaha departs from these:

- **Skips are silent early returns** (107 sites) instead of `#[ignore]`. This is the single biggest problem and it is a convention problem, not a tooling one.
- **Test placement follows no rule.** 95 inline `#[cfg(test)]` modules and 27 extracted files; `sim.rs` carries 2,600 lines of tests below 570 lines of driver; `engine/acmp.rs` is inline and `engine/rules_tests.rs` is extracted with an identical preamble.
- **No `tests/common`**, so nine integration binaries each carry their own allocator harness and their own corpus loader.
- **No committed corpus**, so the fixture tier does not exist: tests are either pure or corpus-bound, with nothing in between.
- **Wall-clock loops in tests** (30 `Instant::now()` sites, six `wait_*` pumps with a 60 s ceiling in the plugin tests) where the offline session already has a virtual clock.

## 3. Recommendations, in order

### R1. Ship an original test corpus and test SoundFonts
The corpus cannot be Yamaha's files, and the free style sites carry no licence that allows redistribution either. So the shippable corpus is generated by yahaha itself, from data yahaha owns.

- **`sff::synthetic`**: a `StyleBuilder` that writes SFF1 and SFF2 files (the parser already reads both). It needs to cover what the tests cover: all 15 sections, CASM with each NTR (Root Trans, Root Fixed, Guitar) and NTT table, chord mute masks, high key and note limits, RTR variants, a section with mid-bar fills and breaks, program and volume changes inside a pattern, pitch bend in a pattern, an SInt block with voices, sends, RPN bend range and one XG part-parameter SysEx, tempo and time-signature variety (3/4, 6/8), an OTS block, and a style with no CASM. `multipad::synthetic::demo_bank()` is the pattern; `capture.rs`'s SMF writer and `multipad/synthetic.rs`'s should be merged into `smf::write` first (review D4) so there is one writer.
- **Commit the generated files** under `tests/fixtures/styles/*.sty` (each a few KB) with a test that regenerates and byte-compares them, so a generator change is a deliberate, reviewed diff and the files are usable from the CLI (`yahaha play tests/fixtures/styles`). Name them after what they exercise (`guitar-ntr.sty`, `no-casm.sff1.sty`, `six-eight-fills.sty`).
- **SoundFonts**: `patches::sf2::tiny_sound_font()` already exists. Extend it to a `tests/fixtures/soundfonts/` set: one General MIDI-shaped font with a preset on every bank 0 program and a drum bank (single-cycle waves, tiny samples), one with extra banks for the sound-library tests, one deliberately malformed for the parser. Commit them (tens of KB). Keep the tone tests that need a real instrument sample (`tests/synth_velocity_tone.rs`) on GeneralUser GS, downloaded and cached in CI with a pinned version and checksum; its licence allows redistribution but it is too large to commit.
- **Golden listings for the synthetic styles are committed in full**, not as digests. The content is ours, so a change to chord following shows up in the PR as the notes that moved. The digest form stays for the corpus styles.

Outcome: a fresh checkout on any OS runs the fixture tier with real assertions; a corpus-less CI can fail on a chord-following regression.

### R2. Make every skip explicit, and count them
- Replace the 107 early returns with `#[ignore = "corpus: <style>"]` on the tests that genuinely need a Yamaha style, and with the synthetic fixture on the ones that only need *a* style (most of them: they test the engine, not the style). The split is the work; the reviewer's list in `review-2026-09-27.md` D7 names the files.
- One `testkit::corpus(rel)` for the remaining corpus tests that panics with a clear message when the file is missing (an ignored test that runs under `--include-ignored` should fail loudly, never skip).
- The owner's gate runs `cargo test --profile test-fast -- --include-ignored` on the machine with the corpus; CI runs the default set. Both print the ignored count, which becomes the visible number of tests the run did not exercise.
- With `cargo-nextest`, name the tiers in a filterset (`corpus`, `hardware`, `plugin`) in `.config/nextest.toml` so `cargo nextest run -E 'not test(/corpus/)'` is the CI command and the report lists what was skipped by name.

Outcome: `grep -rn 'skipping' src tests` returns nothing; the vacuous count in §1 goes from about 426 to 0; a green run means every non-ignored test asserted something.

### R3. Tiers, by dependency, and which runner runs each

| Tier | Needs | Marker | Linux CI | macOS CI | Owner gate |
|---|---|---|---|---|---|
| T0 pure | nothing | none | yes | yes | yes |
| T1 fixture | `tests/fixtures/` (committed) | none | yes | yes | yes |
| T2 plugin | an Audio Unit; `DLSMusicDevice` ships with every macOS, runners included | `#[cfg(feature = "plugins")]` (already) | not built | yes | yes |
| T3 corpus | `corpus/` (Yamaha, git-ignored) | `#[ignore = "corpus: …"]` | ignored | ignored | `--include-ignored` |
| T4 real font | GeneralUser GS | `#[ignore = "soundfont: GeneralUser GS"]` | cached download, `--include-ignored` on that binary | same | yes |
| T5 hardware | CoreMIDI devices, audio output | `#[ignore = "hardware"]` (`devices_live.rs` already is) | no | no | on request |

The macOS job should run T2 plus anything under `cfg(target_os = "macos")` and stop there; the bulk (T0, T1) is identical on both platforms and belongs on the cheap runner. `cargo test --features plugins plugin` (a name filter) or a nextest filterset keeps the macOS job to a few minutes.

### R4. One placement rule
- A test module stays inline only while it needs private items *and* is under about 100 lines; otherwise it is `<module>/tests.rs` (or `<name>_tests.rs`, the convention `engine/` and `session/` already use). Apply it once: `sim.rs`, `live.rs`, `synth.rs`, `theory.rs`, `capture.rs`, `sff.rs`, `session/fx.rs`, `session/style_change.rs`, `session/controllers.rs` move out.
- `src/sim.rs` splits into the driver (`sim/mod.rs`, `recorder.rs`, `script.rs`) and its tests; the three `sim_*_tests.rs` files at the crate root move under `sim/`.
- Tests of behaviour through `AppCmd` and `Session::offline` belong in `tests/` (they are integration tests of the public API); tests that reach into `Engine` fields stay in-crate.

### R5. `testkit` and `tests/common`
One in-crate `#[cfg(test)] pub(crate) mod testkit` and one `tests/common/mod.rs` replace the 52 fixture functions, 18 sinks, 21 stepping helpers, 17 `const MS`, the nine allocator preambles and the three `energy()` copies. The proposed surface (fixture loaders, `offline()`, `Recorder` with `ons/offs/cc` accessors, `Null` sink, `bar_ns`, `play_grid`/`play_deadlines`/`run_loop`, `until`, MIDI byte builders, `chord("Am7")`, `temp_dir(tag)`, the per-thread counting allocator) is in `review-2026-09-27.md` D7. Also `impl Default for engine::Snapshot`, so the two 46-field literals become struct-update expressions.

### R6. Virtual time in place of wall-clock waits
The offline session advances by `advance(ns)`. The six `wait_*` loops in the plugin tests and the 30 `Instant::now()` sites should drive that clock and assert within a bounded number of steps; where a real thread is involved (plugin load), the test waits on the channel the code already exposes, with the 60 s ceiling as a last resort in one helper. This removes the only flakiness source the reviewers found.

### R7. Extend the strong patterns
- **Property tests** for the recognizer and transposer (`proptest`: transpose by n then by 12-n returns the input; any 1 to 10 keys never panics; `Chord::pack`/`unpack` round-trip), and for the SFF, SF2 and Multi Pad parsers ("arbitrary bytes never panic", which the byte-flip loops approximate today).
- **Table pinning** as `controllers::FUNCTIONS` does: add the same kind of test for the `Led`/`Look` pair and the `FxType` ordering contract (review D2, D5).
- **Full golden listings** (R1) for the synthetic styles, one per fixture style, run in T1.
- A **Linux-only test module** for `midi/null.rs` and the `rt` shim, so the port has coverage of its own.

## 4. GitHub Actions: macOS runners for the AU tests
GitHub provides hosted macOS runners. `macos-latest` is Apple Silicon (arm64), and `macos-13`/`macos-15-intel` are x86_64 for testing the other architecture. For a public repository the minutes are free; for a private one macOS minutes bill at ten times the Linux rate, which is the reason to keep the bulk on Linux. `build/linux-ci`'s `ci.yml` already has a `macos-latest` job that runs the full suite with `--features plugins`; the change is to narrow that job to T2 and the `cfg(target_os = "macos")` code, and to leave T0 and T1 to the Linux job.

What works on a hosted macOS runner: `DLSMusicDevice` (the AU the plugin tests use) is part of macOS, CoreMIDI virtual endpoints work without hardware, and `--features plugins` builds. What does not: there is no audio output device, so anything that opens the default cpal device must be offline (the tests already use `offline_audio`), and third-party AUs are not installed. `Swatinem/rust-cache` and the `test-fast` profile keep the job short; expect the plugin build to dominate.

## 5. What "done" looks like
- `tests/fixtures/` holds generated styles and SoundFonts with a regeneration test; `docs/fixtures/README.md` says what each exercises.
- `grep -rn 'skipping' src tests` is empty; the corpus tests are `#[ignore = "corpus: …"]`; CI prints their count.
- Linux CI fails on a chord-following change to a synthetic style (prove it once by breaking `theory::transpose` on a branch).
- The macOS job runs the plugin tests only and finishes in under ten minutes.
- One placement rule, one `testkit`, one `tests/common`, no `const MS` outside them.
